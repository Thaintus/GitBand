# GitBind

> 让每个仓库，用对账号。

面向 **Windows** 的本地 Git 身份与凭据管理工具，并提供 **macOS / Linux 实验性打包**。把个人、公司和不同托管平台的账号集中管理，为每个仓库绑定合适的提交身份与认证凭据，减少反复修改 Git 配置的麻烦。

**Windows x64 · SSH / HTTPS · 中文 / English · Apache-2.0**

[下载与安装](#下载与安装) · [快速上手](#快速上手) · [工作原理](#工作原理) · [常见问题](#常见问题) · [参与贡献](#参与贡献)

## 为什么需要 GitBind

同一台电脑上，你可能同时维护个人 GitHub 项目、公司的云效仓库，以及其他 Git 服务上的代码。GitBind 帮你把“这个仓库应该用哪个账号”变成明确、可查看、可切换的配置。

它专注于**账号、仓库和绑定关系**，并提供按账号克隆与快进拉取。提交、推送、分支管理和冲突处理仍由你熟悉的终端或 IDE 完成。

> [!IMPORTANT]
> **提交署名不等于远程权限。** `user.name` 和 `user.email` 决定提交记录中的作者信息；远程服务器根据 SSH Key 或 HTTPS 凭据决定是否允许访问。GitBind 不会替你创建平台账号，也不会授予或撤销服务器上的权限。

## 主要功能

| 功能 | 可以做什么 |
| --- | --- |
| 多账号管理 | 维护账号别名、提交姓名与邮箱、默认账号、HTTPS 凭据和 SSH 私钥 |
| 项目绑定 | 登记本机已有 Git 仓库，选择账号后立即改绑，并查看“绑定账号”和“实际生效账号” |
| 即时搜索 | 账号、项目、平台页面支持输入即过滤已有数据，不区分大小写，清空后恢复完整列表 |
| 全局模式 | 临时使用统一账号，写入 Git 全局配置并同步覆盖已绑定仓库；关闭后恢复原全局配置及各项目绑定 |
| 远程地址维护 | 修改仓库 `origin`，在常规 SSH / HTTPS 地址之间快捷转换 |
| 连接测试 | 使用当前生效配置读取远程引用，辅助排查认证问题 |
| 平台管理 | 通过新增/编辑弹窗维护平台名称与 Host，支持自建服务、启用与禁用；已启用平台优先显示 |
| 托盘与界面 | Windows/macOS 默认关闭后驻留托盘，Linux 默认退出，可在设置中调整；支持简体中文与 English |
| 删除保护 | 账号、项目、平台和 SSH 私钥移除入口统一为右上角 `×`，并提供二次确认 |

## 下载与安装

### 使用安装包

在仓库的 [Releases 页面](https://github.com/thaintus/GitBand/releases)查看发布记录和附件，选择 `GitBinder-<版本号>-setup.exe`。如果尚无发布附件，可按下方的[源码构建](#源码构建)说明自行生成。

- 当前正式发行目标为 **Windows x64**；macOS 提供未公证、待实机验收的实验包，Linux 提供待桌面实机验收的 `.deb` 与便携实验包。
- 安装包自带 .NET 运行时，使用者无需单独安装 .NET SDK 或 Runtime。
- 需要已安装系统 Git；使用 SSH 地址时还需要可用的 OpenSSH。
- 安装向导需要管理员权限，支持选择安装目录及创建快捷方式。
- 当前打包流程未配置代码签名。请核对下载来源；若发布页提供 SHA-256，可与本地文件哈希比对。

安装目录与用户数据目录相互独立。升级前请从托盘菜单退出旧版本，再运行安装程序。

### macOS 实验包

- Apple Silicon（M 系列）选择 `osx-arm64`，Intel Mac 选择 `osx-x64`；目标系统为 macOS 14 或更新版本，自带 .NET 运行时，仍需系统 Git / OpenSSH。
- `GitBinder-<版本号>-osx-<架构>-unsigned.zip` 包含 `GitBinder.app` 和本机签名/DMG 脚本。它不是已经签名、公证及实机验证的正式安装包，不应直接替代稳定发行版。
- 按包内说明先在 Mac 完成本机签名，再将应用固定安装到 `/Applications`。完成认证配置后不要随意移动应用，否则写入 Git 配置的凭据助手路径会失效。
- HTTPS 凭据保存在当前用户登录钥匙串；首次保存、更新应用签名或首次由凭据助手访问时可能需要系统授权。取消授权或钥匙串锁定时操作会失败，不回退为明文存储或其他账号。
- 当前 Windows 环境只能完成跨平台发布与包结构校验；Mac 的启动、钥匙串授权、托盘、克隆/拉取仍需实机验证。详见 [macOS 打包与验收说明](aBase/doc/MACOS_PACKAGING.md)。

### Linux 实验包

Linux 用户请先阅读 [Linux 实验包安装说明](aBase/doc/LINUX_PACKAGING.md)：Ubuntu/Debian 使用与 CPU 对应的 `.deb`，其他发行版需自行满足便携包的原生依赖。程序自带 .NET，但仍需要桌面会话、Git/OpenSSH、libsecret 与已解锁的 Secret Service 密钥环。不要用 `sudo` 启动应用。

### 快速上手

1. **检查环境**：打开“设置”，确认 Git / SSH 路径；需要时点击“重新检测”。
2. **添加账号**：进入“账号”，填写提交姓名和所属平台，提交邮箱可选；按需要填写 HTTPS 用户名与凭据，或导入 SSH 私钥。平台要求 Token 时，请使用相应平台签发的 Token。
3. **添加项目**：进入“项目”并点击“添加项目”，选择本机已有目录；普通目录、未配置远程地址的 Git 仓库均可添加。仅新登记的 Git 仓库会尝试自动绑定已启用的默认账号。
4. **选择账号**：项目可在卡片中选择“绑定账号”，选择后即应用，无需额外保存；普通目录首次绑定会先提示初始化 Git，没有远程地址也可绑定提交身份。全局模式开启时，实际生效账号仍以全局账号为准。
5. **确认连接**：已配置远程地址的 Git 项目可点击账号框旁的“测试”，再回到终端或 IDE 执行自己的 Git 操作。

普通目录显示“本地项目 · 未初始化 Git”，可先分组、修改本地路径或移除。也可直接通过“修改地址”保存 HTTPS/SSH 仓库链接，或选择绑定账号：首次操作确认后会在该目录初始化 Git，保留现有文件，不会自动下载、提交或上传。单纯添加和进入项目页不会初始化或默认绑定；自行初始化 Git 后也可重新进入项目页识别。已有 Git 仓库没有 origin 时，可通过“修改地址”配置后再测试或拉取。修改路径仅用于重新定位同一项目，已有 Git 仓库不能改到普通目录。

数据较多时，可使用账号、项目、平台页面顶部的搜索框。输入部分名称、邮箱、路径、远程地址或主机等对应字段即可过滤；搜索只作用于已加载数据，不发起远程查询，也不会修改记录。

应用弹窗仅保留关闭按钮，不显示最大化/最小化。按 `Esc` 优先收起下拉菜单、取消当前弹窗或项目地址/路径编辑；空闲主页面按 `Esc` 与点击右上角关闭一致，遵循“关闭到托盘”设置。保存期间暂不关闭，克隆进行中按 `Esc` 会先请求取消并等待操作返回，不会直接隐藏后台任务。

> “测试”按项目实际地址和当前生效账号执行只读的 `git ls-remote`，与软件内拉取共用非交互认证，不再先重写仓库配置。若账号认证方式与地址协议不匹配，会先询问是否转换地址；只有确认才会修改本地 origin 及对应账号认证配置。测试成功只说明可以读取远程引用，不代表拥有推送权限，公开仓库也可能允许匿名读取。

## 工作原理

### 有效账号与 Git 配置

应用内部的账号选择顺序为：

```text
全局模式账号 > 项目绑定账号 > 默认账号
```

GitBind 通过仓库本地 Git 配置、Git 全局配置与 `gitbinder-credential`（Windows 下带 `.exe`）配合系统 Git 工作，**当前没有 Git Shim，也不需要替换系统 Git**。

- 普通模式下，为项目应用 `user.name`、`user.email` 及与 Remote 协议对应的认证配置；首次应用前保存相关配置快照。
- 解绑会恢复保存的本地配置。移除项目会先执行解绑，再删除登记记录，**不会删除本地源码或 Git 仓库**。
- 默认账号用于应用内的默认选择和新登记 Git 仓库的自动绑定，不会为未初始化 Git 的项目写配置，也不等于普通模式下接管所有未登记仓库。
- 终端或 IDE 需要使用遵循这些配置的 Git。工具自己的凭据管理、环境变量或命令行覆盖参数可能改变最终行为。

### 提交邮箱隐私

提交邮箱留空表示**新提交不携带邮箱地址**，不是沿用默认或全局邮箱。应用当前生效账号时，会明确写入空的 `user.email`、`author.email` 和 `committer.email`，覆盖继承的邮箱配置；填写邮箱时，三个配置项同步使用该邮箱。全局模式以全局账号为准，普通模式以项目绑定账号为准。

编辑已绑定账号并清空邮箱后，保存会同步相关仓库；若提示“账号已保存，但配置同步失败”，需处理提示并重新保存后再提交。升级后启动软件也会重新应用现有绑定。解绑及关闭全局模式会恢复修改前的配置，包括原来明确设置为空的邮箱。

Git 的新提交身份可表示为 `姓名 <>`，但部分平台或仓库策略可能拒绝空邮箱。此设置不会清除历史提交中的邮箱，也不改写变基、挑拣或修改提交时保留的原作者信息；IDE/终端显式指定的环境变量、`--author`、`-c` 或更高优先级配置仍可覆盖它，不能把它当作对所有工具的强制隐私拦截。行为依据：[Git 官方身份生成实现](https://github.com/git/git/blob/v2.51.0/ident.c)。

### 全局模式

开启全局模式时，会保存并修改当前系统用户的 Git 全局 `user.name`、三个邮箱配置项（`user.email`、`author.email`、`committer.email`）、`core.sshCommand`、`credential.helper`，同时对已绑定仓库应用全局账号。

关闭后恢复原全局配置，并重新应用各项目原有绑定。全局模式不会把项目的绑定关系改成全局账号。

未登记仓库仍遵循 Git 的配置优先级：如果它已有本地身份或认证设置，这些设置可能覆盖全局设置。因此，全局模式不是对所有 Git 工具和仓库的强制拦截。

### SSH 与 HTTPS

账号可以同时录入 SSH 与 HTTPS 认证信息，**实际使用哪一种由项目的 `origin` 地址决定**，不是按填写顺序或固定优先级选择。

```text
SSH    git@github.com:your-org/your-repo.git
HTTPS  https://github.com/your-org/your-repo.git
```

在“修改地址”中使用协议切换按钮，只会改变编辑框内容；点击“保存地址”后才会写入仓库。自定义端口等非标准地址需要手动填写。

切换项目绑定账号后，或点击“测试”时，如果 origin 使用 HTTPS 而生效账号只有 SSH 凭据（反向同理），会弹窗展示原地址与转换后的地址，确认后再切换。取消保留原地址及已经保存的账号绑定，并停止本次测试。全局模式按全局生效账号判断，不批量静默修改仓库地址；双协议账号继续使用原地址的协议。单项和分组拉取均使用当前分支实际跟踪的远程，不为匹配认证方式自动改写 origin；不匹配时请补齐账号凭据或手动修改正确远程的地址。

编辑账号时，HTTPS 凭据留空保留已有凭据及认证能力，不需要重复填写。账号提交姓名/邮箱不是平台认证凭据；IDE/终端能拉推，也不代表 GitBind 已录入相同的认证信息。

修改地址不会搬迁远程代码或自动更换绑定账号。迁移托管平台后，请确认目标仓库已准备好、地址和绑定账号正确，再点击“测试”验证远程连接。

> [!WARNING]
> 平台分类不是权限隔离边界，GitBind 允许跨平台绑定账号。只向可信的 Remote 使用账号凭据，尤其是在开启全局模式或修改 HTTPS 地址时：当前按账号固定的 HTTPS Helper 不会以账号所属平台的 Host 限制凭据返回。

## 数据与安全

账号和项目管理不依赖自建后端，不需要注册 GitBind 云端账号；本地管理可离线进行，远程连接测试以及你自己的拉取、推送仍需要网络。当前未接入遥测或自动更新服务。

Windows 用户数据默认位于：

```text
%LOCALAPPDATA%\GitBinder\
├── gitbinder.db   # 账号、项目、绑定、配置快照及机密引用等元数据
├── secrets\      # Windows DPAPI CurrentUser 加密后的机密
└── keys\         # 导入的 SSH 私钥文件副本
```

macOS 实验版使用 `~/Library/Application Support/GitBinder/` 存放数据库与私钥副本，凭据保存在系统登录钥匙串，不生成 Windows DPAPI 密文。导入的私钥目录权限为 `0700`、文件为 `0600`。Windows 数据目录不能直接复制到 Mac 作为凭据迁移方案。

Linux 实验版使用 `$XDG_DATA_HOME/GitBinder/`（未设置或不是绝对路径时为 `~/.local/share/GitBinder/`）；凭据经 libsecret 存入当前用户的 Secret Service 密钥环，不保存到明文文件。需要可用的会话 D-Bus 及 Secret Service 服务；前台保存可能要求创建/解锁密钥环并授权，后台助手读取不主动解锁，缺少服务或锁定时失败，不回退其他账号。私钥目录/文件权限分别为 `0700`/`0600`；不要混用不同用户或不一致的 XDG 环境启动桌面程序与凭据助手。密钥环不提供对同一登录用户下其他应用的强隔离。

- HTTPS 密码 / Token 通过机密存储加密保存，数据库记录其引用，不把这些凭据写进 Git 配置。
- **SSH 私钥是导入文件的副本，不是 DPAPI 加密文件。** 请保护私钥和数据目录的访问权限，不要把它们提交到仓库。
- DPAPI 密文与当前 Windows 用户上下文相关，不要把直接复制数据目录当作可靠的跨用户、跨设备凭据迁移方案。
- 退出应用不会撤销已经写入的 Git 配置。卸载前，建议先关闭全局模式，并解绑需要交回系统管理的仓库，避免配置继续指向被卸载的凭据组件。
- 反馈问题时请先脱敏：不要上传 Token、密码、私钥、真实用户数据库或含机密的完整 Git 配置。

## 常见问题

### 为什么切换了 GitHub 账号，仍能向云效提交或推送？

本地 `commit` 的作者信息和远程 `push` 的认证是两件事。把账号分类设为 GitHub 不会自动撤销它在其他服务器上的权限。如果实际使用的密钥或凭据也被云效接受，推送仍可能成功。请同时核对项目的 Remote、实际生效账号和服务器端授权。

### 能直接克隆仓库吗？

可以。在项目页点击带分支图标的“克隆仓库”，在弹窗中填写 HTTPS/SSH 仓库地址，选择绑定账号、已有父目录和新文件夹名称，然后点击“开始克隆”。弹窗内显示进度并提供取消传输，失败时保留输入及可选择复制的错误信息；成功后关闭并刷新项目列表。全局模式下认证仍以全局账号为准，所选账号作为项目绑定保留。此入口按地址克隆，不通过平台 API 枚举仓库。已有目录继续使用“添加项目”登记。

项目卡片上的“拉取”使用当前生效账号，按当前分支的 remote/merge 跟踪设置快进更新，支持非 origin 远程。尚未设置跟踪时，已有提交的分支仅尝试 origin 同名分支；尚无提交的仓库查询 origin 的默认分支，再拉入当前本地分支。成功后才保存跟踪设置；配置不完整、不存在目标分支时明确报错，不猜测其他分支。已有本地改动或未跟踪文件时，让 Git 判断能否安全更新，如果会覆盖本地文件则停止。正在合并/变基、分离 HEAD 或历史分叉时也会停止；不自动 stash、reset、变基或生成合并提交。子模块不递归更新。项目路径左侧的文件夹图标可直接在资源管理器/系统文件管理器中打开该目录，不修改项目路径。

项目页的“分组”侧栏支持新建、重命名和删除分组。点击加号或铅笔图标，在弹窗中填写分组名称。通过项目本地路径右侧的下拉框设置分组，选择后立即保存；“全部项目”始终显示，“未分组”仅在有未分组项目时显示，分组筛选可与搜索叠加。项目下拉框始终保留“未分组”，可用于取消归类。删除分组需确认，仅将项目移回未分组，不删除代码或解绑账号。

每个分组都有向下箭头形的“拉取”图标按钮，悬停可查看说明：确认后依次更新该组全部项目（不受搜索筛选影响），每项沿用当前生效账号和快进保护。未初始化 Git、未配置远程地址或其他失败均在逐项结果中提示，不阻断其他项目；支持取消，并显示成功、失败、未完成数量及逐项结果。操作结果弹窗中的文字可直接选中后按 `Ctrl+C` 复制。

单个项目操作只锁定当前卡片的相关操作，其他项目、搜索、分组切换和打开目录仍可用；不同项目可同时拉取，当前项目的测试/拉取进度与取消入口独立显示。取消只影响所选项目，刷新保留其他卡片正在编辑的内容。分组批量拉取、分组结构修改及全局模式切换保留必要的跨项目冲突保护。

项目操作期间，账号保存、设默认和删除也会受到冲突保护，避免运行中更换身份或凭据。若提示无法确认 Git/SSH 已退出，请先确认相关进程停止再重试；不能把该提示当作普通取消。改绑保存失败会尝试恢复本次操作前的配置，恢复失败时请先核对仓库本地身份与认证配置。

传输期间显示状态并允许取消，单次最长等待 30 分钟。克隆目标必须尚不存在；失败或取消后可能留下部分文件，不会自动清理。若已克隆但登记/绑定失败，按提示使用“添加项目”或重新选择绑定账号，避免重复克隆。

认证按地址协议执行：HTTPS 使用当前账号的凭据助手，SSH 只指定当前账号私钥；两种凭据都录入时仍以地址协议为准。传输保留本机 Git 的全局/系统配置读取，兼容代理、CA、证书后端、safe.directory 和 insteadOf 地址重写；认证仍显式固定当前账号，不回退其他 Git helper 或私钥。SSH 使用同一定位后的程序解析本机连接设置，保留 HostName、端口、ProxyCommand/ProxyJump 与 known_hosts 等设置，但目标主机不复制其他 IdentityFile。SSH 不弹出口令/信任对话框：首次连接需在可信终端验证主机，带口令私钥需提前由 Agent 解锁同一密钥；不能直接借用 IDEA 内部保存的密码或会话。不支持 HTTP、不绕过主机校验或自动接受未知主机，不把密码/Token 放入 URL。分叉时仍只允许快进，不替代 IDEA 的合并/变基和冲突处理。

Windows 传输优先使用所选 Git 安装目录配套的 OpenSSH，配置解析和实际连接使用同一程序；找不到配套程序时才使用系统 SSH 定位结果，macOS/Linux 保持原规则。这样可避免 IDE 使用 Git 自带 SSH、软件却使用 Windows OpenSSH 导致密钥权限或代理行为不一致。本机私钥权限、格式、口令和代理签名错误会单独提示，不再一律归为服务器认证拒绝；不会自动修改私钥文件权限或切换其他账号。

### 关闭窗口后为什么还在运行？

Windows / macOS 默认隐藏到系统托盘，可从托盘菜单选择“退出 GitBind”，或在设置中关闭托盘驻留。Linux 桌面不一定提供托盘宿主，因此默认关闭窗口即退出；确认桌面有托盘支持后，可手动开启驻留。关闭窗口或退出进程都不等于关闭全局模式。

### 项目目录移动了怎么办？

在项目卡片底部点击“修改本地路径”，输入或选择移动后的仓库目录，点击“保存路径”并确认。应用会校验 Git 仓库并按真实仓库根目录检查重复登记，同时更新远程信息，保留项目 ID、名称、账号绑定及原配置快照；不会移动或删除文件，也不会改写 Git 配置。此功能只用于移动后的同一仓库，不应指向其他仓库或新克隆副本；保存后可点击“测试”验证当前生效账号。

进入项目页时会从本地 Git 仓库同步 origin 地址、协议和主机，不联网。未配置 origin 会显示提示；读取失败时保留上次保存的信息并显示原因，不会把已有 HTTPS 信息静默清空。

## 源码构建

### 开发环境

- Windows、.NET 10 SDK、系统 Git；SSH 相关功能还需 OpenSSH。
- 生成安装包时需要 Inno Setup 6，并确保其 `Languages` 目录包含 `ChineseSimplified.isl`。
- 首次还原依赖需要能够访问 NuGet。

```powershell
git clone https://github.com/thaintus/GitBand.git
cd GitBand

dotnet build GitBinder.slnx -c Debug
dotnet test GitBinder.slnx -c Debug --no-build
```

也可以使用仓库脚本完成还原、构建和测试：

```powershell
.\build\build.ps1
```

### 本地运行与发布

完整的 HTTPS 认证需要桌面程序与 `gitbinder-credential.exe` 位于同一目录。推荐用发布脚本同时生成两个程序，再启动桌面程序；仅对 Desktop 执行 `dotnet run` 不会自动准备凭据组件。

```powershell
# 版本号为示例，可按本次发布计划调整
.\build\publish.ps1 -Version 1.2.5
.\build\publish\app\GitBinder.Desktop.exe
```

发布输出位于 `build/publish/app/`；发布脚本会重新生成该临时目录。

> [!CAUTION]
> 开发版与安装版默认共用当前 Windows 用户的数据目录。应用启动时会重新应用已有绑定及全局模式，不是隔离的演示环境。涉及真实 Git 的开发验证请使用专用 Windows 测试用户和临时仓库；集成测试必须隔离 `GIT_CONFIG_GLOBAL`，不要修改开发机真实全局配置。

### 生成安装包

```powershell
# 同时发布 Desktop 与 Credential Helper，再生成 Windows x64 安装包
.\build\build-installer.ps1 -Version 1.2.5
```

输出为 `dist/GitBinder-1.2.5-setup.exe`。请为新发行版指定新的版本号，避免覆盖同名历史产物。该命令负责发布和打包，**不执行单元测试**。

1.2.5 已单独执行打包前后 691 项逻辑测试、并发重复回归和隔离 UI 验证，实际范围、校验值与未验证边界见 [迭代记录](aBase/iteration/V1-首版开发.md)。隔离回归不代表覆盖安装或真实远程账号操作已验收。

如需串联构建、测试和打包：

```powershell
.\build\build.ps1 -Configuration Release -Package -Version 1.2.5
```

### Linux 实验包构建

Linux 实验包使用独立入口 `./build/build-linux.ps1 -Version 1.2.0`，默认生成 x64/ARM64 的 `.deb` 和 `.tar.gz`，不执行测试，不覆盖历史产物。具体依赖、安装路径与验收边界见 [Linux 打包文档](aBase/doc/LINUX_PACKAGING.md)。

### 移动源码目录

解决方案和项目引用使用相对路径；构建脚本通过自身所在目录定位仓库，安装包脚本也使用相对路径。移动或重命名源码目录后，从新位置重新打开解决方案即可，无须替换源码中的工作区盘符或目录名。Git、SSH 和 Inno Setup 的常见安装目录通过 Windows 系统目录定位，不依赖固定的 `C:` 盘或用户名。

注意：IDE 最近打开记录、`bin/obj` 编译缓存及旧 PDB 可能仍包含原路径，不应将生成文件中的绝对路径手工改成相对路径。后续需要构建时，在新目录重新还原与构建；若仍有旧路径错误，再清理对应构建缓存。

运行时路径与源码引用不同：用户数据库和凭据位于 `%LOCALAPPDATA%/GitBinder/`，不会随源码移动；已登记仓库路径、SSH 私钥路径和写入 Git 配置的凭据助手路径需要稳定定位，不能改为依赖当前工作目录的相对路径。如果也移动了受管理仓库、私钥或开发版程序，应核对对应配置；不要直接批量替换数据库或 Git 配置。

## 项目结构

项目使用 C# / .NET 10、Avalonia、CommunityToolkit.Mvvm、SQLite，以及系统 Git / OpenSSH。

```text
GitBinder.slnx
├── src/
│   ├── GitBinder.Desktop/           # 窗口、页面、ViewModel、本地化与组合根
│   ├── GitBinder.Application/       # 用例编排与端口接口
│   ├── GitBinder.Domain/            # 实体、领域规则与有效账号决策
│   ├── GitBinder.Infrastructure/    # Git CLI、SQLite 等外部能力实现
│   ├── GitBinder.Platform/          # DPAPI / Keychain / Linux Secret Service、路径和私钥导入
│   └── GitBinder.CredentialHelper/  # Git Credential Helper 可执行程序
├── tests/GitBinder.Tests/          # 单元测试、Fake 与隔离的 Git 集成测试
├── build/                         # 构建、发布和 Inno Setup 脚本
├── aBase/                         # 设计、迭代及 Schema 参考资料
└── LICENSE                        # Apache License 2.0
```

核心依赖方向为 `Desktop → Application → Domain`。Infrastructure 和 Platform 实现端口，通过依赖注入组装；Domain 不依赖 UI、数据库或平台 API。

## 参与贡献

欢迎通过 [Issues](https://github.com/thaintus/GitBand/issues)反馈问题、提出建议，或提交 Pull Request。

- **反馈缺陷**：提供应用版本、Windows / Git 版本、使用协议、全局模式状态、复现步骤与脱敏后的错误信息。
- **提出功能**：先说明使用场景；较大的改动建议先开 Issue 沟通，保持项目聚焦于身份与凭据管理。

- **说明验证范围**：在 PR 中注明实际执行过的检查与测试；静态检查、单元测试和真实远程认证不能互相替代。

涉及安全问题时，请勿在公开 Issue 中粘贴敏感信息或可直接利用的细节。
